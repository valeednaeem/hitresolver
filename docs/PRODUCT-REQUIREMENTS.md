# HitResolver — Product Requirements (Demo v0.1)

**Product:** HitResolver
**Tagline:** Make Better Decisions, Every Day!
**Positioning:** An AI-assisted decision intelligence platform that helps people organize alternatives, evaluate trade-offs, compare possibilities, and make better-informed decisions.

---

## 1. Product Philosophy (non-negotiable)

HitResolver does **not** make decisions on behalf of people. It helps people make decisions they can understand, evaluate, and explain.

AI supports human reasoning; it never pretends to know the objectively correct answer.

The product must distinguish three kinds of content, visibly and at all times:

| Label | Meaning | Rule |
|---|---|---|
| **FACT** | Information supplied or confirmed by the user | May be presented as given |
| **ASSUMPTION** | Estimated, uncertain, or incomplete information | Must be labelled as an assumption |
| **AI SUGGESTION** | Generated by a model | Must be labelled, and always editable / rejectable / acceptable |

**Never** present an assumption or a generated suggestion as a verified fact.
**Never** present a calculated score as an objectively correct decision.

### Audiences
Individuals · Students · Professionals · Entrepreneurs · Small businesses · Teams & organizations

---

## 2. Scope Boundary

**This release is a demo.** It is for product demonstrations, early feedback, concept validation, UX evaluation, feature testing, and investor/client presentations.

It is **not**: a commercial SaaS, a cloud product, or a production system.

---

## 3. Required Functional Scope

### A. Application shell
- [ ] HitResolver branding and visual identity
- [ ] Main workspace with decision navigation/sidebar
- [ ] Responsive layout: desktop, tablet, mobile
- [ ] Consistent design system (type, spacing, colour, cards, buttons, forms, tables, badges, modals, nav, breakpoints, icons)
- [ ] Loading, empty, error, and success states
- [ ] Accessible forms and controls

### B. Multi-Decision Workspace
- [ ] Create decisions
- [ ] Rename decisions (title)
- [ ] Edit descriptions
- [ ] Switch between decisions
- [ ] Duplicate decisions
- [ ] Delete decisions **with confirmation**
- [ ] View recently updated decisions (ordered)
- [ ] Save changes automatically
- [ ] Load an example decision preset
- [ ] Persistence appropriate to demo architecture, with **documented limitations** — no implication of cloud sync

### C. Weighted Pros & Cons
- [ ] Add advantages and disadvantages
- [ ] Assign impact weights
- [ ] **Edit** entries
- [ ] Remove entries
- [ ] View total positive and negative points
- [ ] Live balance indicator
- [ ] Descriptive result: Strong Go / Lean Yes / Balanced / Lean No / Strong No
- [ ] **Transparent scoring** — show how the result is calculated
- [ ] Result must never be presented as an objectively correct decision

### D. Weighted Comparison / Decision Matrix *(signature feature)*
- [ ] Add and remove alternatives
- [ ] Add and remove evaluation criteria
- [ ] Rename alternatives and criteria
- [ ] Assign criterion weights
- [ ] Score alternatives 1–10
- [ ] Add contextual notes
- [ ] View weighted totals, percentages, and rankings
- [ ] Identify the leading alternative
- [ ] Inspect score breakdowns
- [ ] **Deterministic scoring with a documented, consistent method**
- [ ] Handle safely: missing scores, zero weights, invalid values, ties, incomplete matrices
- [ ] Interface explains how the weighted result is calculated
- [ ] Foundation laid for future sensitivity analysis
- [ ] Leading score framed as *"a result of your chosen criteria and weights"*, **not** proof of universal bestness

### E. SWOT Analysis
- [ ] Four sections: Strengths, Weaknesses, Opportunities, Threats
- [ ] Add / **edit** / remove entries
- [ ] High, Medium, Low impact levels
- [ ] Clear internal (S/W) vs external (O/T) categorisation
- [ ] Responsive 2×2 layout

### F. HitResolver Verdict Dashboard
Combines: Pros & Cons balance · Comparison ranking · SWOT posture · High-impact risks · Potential opportunities · **Missing or incomplete information** · Suggested next actions

- [ ] Uses deterministic calculations and **transparent rules**
- [ ] Does **not** add unrelated scores together and call it a scientific verdict
- [ ] Clearly distinguishes **calculated results** from **interpretations** and **recommendations**

### G. Decision Reports & Data Portability
- [ ] Markdown decision report export — **including the Verdict Dashboard**
- [ ] JSON backup
- [ ] JSON restoration with **input validation** and **import error handling**
- [ ] Clear success/failure notifications
- [ ] **Never silently overwrite existing decisions** — restoration requires an explicit user choice

### H. AI Decision Assistant
Capabilities the demo must be architected to support:
understand the decision · break it into smaller questions · suggest alternatives · suggest criteria · draft Pros & Cons · identify risks · assist SWOT · detect missing information · explain trade-offs · summarise results · suggest next steps.

- [ ] AI suggestions are **editable** and **never overwrite user content without permission**
- [ ] Integration approach decided only **after** inspecting available infrastructure
- [ ] If a provider is configured: integrate **securely through a server-side boundary**
- [ ] If not: build an **honest, clearly labelled** demo experience and document what is simulated
- [ ] **Never** fabricate an AI response and represent it as real
- [ ] **Never** expose API keys or credentials in browser code

## 4. Design & UX Direction

**Communicate:** clarity · confidence · intelligence · simplicity · professionalism · trustworthiness.

**Avoid:**
- Overcrowded dashboards
- Excessive gradients
- Unnecessary animations
- Tiny text
- Inconsistent spacing
- **Placeholder controls that do nothing**
- **Fake charts or statistics**
- **Dead navigation links**
- **Buttons without implemented actions**

> Every visible interactive control must work, or be clearly marked as unavailable.

Must work correctly on desktop, tablet, and mobile. Usability over animation.

---

## 5. Acceptance Definition

A feature is **complete only when all seven hold:**

1. Expected behaviour is implemented
2. Validation works
3. Error cases are handled
4. Relevant tests pass
5. It works with the surrounding application
6. No known critical regression
7. Documentation updated where necessary
